# 飯友配對功能設計

日期：2026-10-07

## 1. 產品定位

這是一個以「餐廳與用餐意向」為核心的純交友飯友平台，不提供戀愛配對，也不依性別或外貌自動排序。使用者可以先決定想吃的餐廳，再查看現在、稍後或明天也想吃該餐廳的人，選擇發送一對一邀請、邀請對方加入多人飯局，或申請加入公開飯局。

產品以手機 App 體驗為主；HTML Demo 在電腦瀏覽器中以置中的手機尺寸呈現。

## 2. 目標

- 把既有「今天吃什麼」餐廳推薦流程延伸成社交共餐流程。
- 支援現在、稍後指定時間與明天的用餐意向。
- 支援一對一與 2–6 人多人飯局。
- 讓使用者在邀請前看到對方照片、基本資料、飲食偏好與可信度資訊。
- OpenAI API 暫不接入 Demo，但保留自然語言解析的資料介面。
- 不公開個人即時座標、電話或外部社群帳號。

## 3. 非目標

- 第一版不做付款、訂位、餐費分帳或店家後台。
- 第一版不做戀愛配對、滑卡、顏值評分或外貌推薦。
- Demo 不建立真實帳號、不傳送真實訊息、不儲存真實個資。
- Demo 不呼叫 OpenAI API，AI 結果以本地預設回應模擬。

## 4. 核心使用流程

### 4.1 從「今天吃什麼」開始

1. 使用者按住麥克風或輸入「明天午餐想吃鹹的，預算 100 元」。
2. AI 需求解析介面輸出餐別、時間、口味、預算及交通偏好。
3. 既有 JEV 引擎依營業時間、距離、評分、預算與口味排序餐廳。
4. 餐廳卡顯示「有幾人想吃」與最近的公開飯局。
5. 使用者進入餐廳頁查看飯友與飯局。

### 4.2 從「附近有人想吃」開始

1. 使用者從首頁切換至飯友頁。
2. 顯示附近餐廳及每間餐廳的現在／稍後／明天意向人數。
3. 使用者進入餐廳頁，查看飯友卡或公開飯局。

### 4.3 一對一邀請

1. 使用者打開飯友資料。
2. 選擇用餐時間，輸入一則邀請訊息。
3. 系統檢查雙方時段是否重疊，以及對方是否仍有有效意向。
4. 邀請送出後等待對方接受、婉拒或逾時。
5. 接受後建立該餐廳與時段專屬聊天室。

### 4.4 多人飯局

1. 發起人選擇餐廳、時間、人數上限與飯局簡介。
2. 飯局可公開接受申請，或由成員邀請特定飯友。
3. 發起人審核申請；額滿後停止接受新成員。
4. 已接受成員進入群組聊天室。

## 5. 資訊架構與畫面

### 5.1 底部導覽

- 吃什麼：語音／文字需求、餐廳推薦。
- 找飯友：附近有用餐意向的餐廳與公開飯局。
- 飯局：收到的邀請、送出的邀請、已加入飯局。
- 我的：照片、興趣、飲食偏好、驗證與共餐紀錄。

### 5.2 Demo 畫面

1. **首頁**：語音輸入、文字範例、推薦餐廳、附近熱門飯局。
2. **AI 解析畫面**：展示輸入如何轉成時間、口味、預算與距離條件，清楚標註 Demo 模擬。
3. **餐廳推薦頁**：距離、評分、價位、營業狀態、JEV 分數與想吃人數。
4. **餐廳詳細頁**：餐廳資訊、時間分頁、飯友卡、公開飯局。
5. **飯友資料頁**：照片、暱稱、18+ 年齡區間、興趣、用餐風格、準時率、評價與驗證。
6. **邀請底部面板**：一對一／多人模式、時間、邀請訊息與確認按鈕。
7. **飯局頁**：成員、名額、餐廳、時間、邀請狀態與示範聊天室。

## 6. 資料模型

### User

- `id`
- `displayName`
- `ageRange`
- `photoUrl`
- `bio`
- `interests[]`
- `foodPreferences[]`
- `dietaryRestrictions[]`
- `mealStyle`
- `verificationStatus`
- `mealCount`
- `onTimeRate`
- `rating`

### Restaurant

- `id`
- `name`
- `lat`, `lng`
- `distanceMeters`
- `rating`, `ratingCount`
- `priceEstimate`
- `categories[]`
- `openingStatus`

### MealIntent

代表某位使用者想在某時間吃某間餐廳；它是本功能的核心資料。

- `id`
- `userId`
- `restaurantId`
- `startAt`, `endAt`
- `partyPreference`: `one_to_one | group | either`
- `budget`
- `message`
- `status`: `active | matched | expired | cancelled`
- `expiresAt`

### MealGroup

- `id`
- `restaurantId`
- `hostUserId`
- `startAt`
- `capacity`
- `memberIds[]`
- `description`
- `visibility`: `public | invite_only`
- `approvalRequired`
- `status`

### Invitation

- `id`
- `senderUserId`
- `recipientUserId`
- `restaurantId`
- `mealIntentId`
- `mealGroupId`（多人飯局時使用）
- `message`
- `proposedAt`
- `status`: `pending | accepted | declined | expired | cancelled`
- `expiresAt`

### Conversation

- `id`
- `invitationId` 或 `mealGroupId`
- `memberIds[]`
- `messages[]`
- `expiresAt`

## 7. 推薦與配對邏輯

### 7.1 餐廳排序

餐廳仍由可解釋的 JEV 引擎排序，建議預設權重：

- 距離／交通時間：30%
- 店家評分：25%
- 預算符合度：20%
- 口味符合度：15%
- 營業可靠度：10%

店家評分資料未接入前，Demo 使用明確標示的模擬資料；正式版需由授權的店家資料來源取得。

### 7.2 飯友排序

飯友不使用外貌、性別或敏感屬性排序。排序條件為：

- 時間重疊程度
- 雙方到餐廳的便利程度
- 預算與飲食限制相容性
- 用餐風格與興趣重疊
- 準時率及共餐信用
- 是否完成真人與手機驗證

只顯示使用者主動發布的有效用餐意向，不因靠近餐廳就自動曝光。

## 8. AI 邊界

### Demo

- 語音按鈕播放模擬錄音狀態。
- 本地規則把固定範例轉成結構化條件。
- 介面清楚標示「AI Demo 模擬」。

### 正式版

- 瀏覽器或原生 App 將語音轉成文字。
- 後端把文字送至 OpenAI，要求依固定 JSON Schema 回傳條件。
- 後端驗證模型輸出，無效欄位回退至預設值。
- OpenAI 只負責理解需求與產生邀請訊息建議，不負責存取完整使用者資料，也不直接決定是否配對。
- API 金鑰只存在後端環境變數，不進入 HTML 或 App Bundle。

## 9. 安全與隱私

- 僅限 18 歲以上使用。
- 公開照片需為本人；正式版至少進行手機驗證，真人驗證作為進階標章。
- 不顯示使用者即時位置與住址，只顯示共同選擇的公開餐廳。
- 邀請接受前不得交換電話或外部社群帳號；可對常見聯絡資訊提示風險。
- 同一對象、同一飯局被拒絕後不得重複邀請。
- 提供封鎖、檢舉、退出飯局與取消邀請。
- 飯局必須在公開營業場所，不支援私人住宅地址。
- 用餐意向與邀請自動過期，避免長期暴露行程。
- 評價只允許實際完成同一飯局的雙方留下。
- 個人頁不顯示完整生日、公司、學校、住址等可識別資料。

## 10. Demo 視覺設計

- 延續既有暖橘色飲食品牌，但社交功能加入柔和綠色作為「有人同行」狀態。
- 主要手機畫布寬約 390px，桌面版以柔和背景置中展示。
- 照片可見但不做大幅全螢幕滑卡；照片只是飯友卡的一部分。
- 餐廳仍是主要視覺主角，飯友以橫向卡片或名單呈現。
- 使用底部導覽、底部邀請面板及清楚的時間分頁，模擬原生 App 操作。
- 支援窄螢幕與桌面鍵盤操作，不產生橫向捲動。

## 11. 錯誤與空狀態

- 無符合餐廳：建議放寬距離、預算或口味。
- 餐廳目前無飯友：可發布自己的用餐意向並等待通知。
- 邀請已失效：重新確認對方意向，不沿用舊聊天室。
- 飯局額滿：提供候補或建立同餐廳新飯局。
- AI 無法理解：保留原始文字，讓使用者手動修正條件。
- 定位失敗：允許手動選擇區域，不使用假精確位置冒充真實定位。

## 12. Demo 驗收條件

- 可從首頁完成語音模擬並看到解析條件。
- 可查看至少三間餐廳並依距離／評分排序。
- 可進入餐廳頁切換現在、稍後、明天。
- 可查看飯友完整資料與照片。
- 可送出一對一邀請。
- 可建立或加入多人飯局。
- 可在邀請／飯局頁看到狀態改變。
- 桌面瀏覽器可操作完整流程，手機寬度 320–430px 無水平溢出。
- 所有 AI、評分與個人資料均清楚標示為 Demo 模擬資料。
